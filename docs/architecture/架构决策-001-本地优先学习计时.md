# ADR-001：本地优先与长期累计计时

- 状态：已接受
- 日期：2026-08-03

## 背景

Egangnal 是单人、本地使用的 macOS 应用。日语和英语空间需要分别维护类似 Steam 游戏游玩时长的长期累计值，同时又不能引入手工修改、单次会话历史或云端同步。

计时必须处理空间切换、应用失去焦点、重新激活、窗口关闭、系统休眠和异常退出。如果让页面自行计时，会产生重复累计和状态冲突。

## 决策

### 1. 本地数据与文件分离

- 使用 SwiftData 保存语言空间、累计秒数、资料元数据和个人资料等结构化状态。
- 使用 Application Support 下的应用专属目录保存导入的 Markdown 和纯文本副本。
- 不启用 CloudKit 或其他网络同步。
- 存储访问通过仓储或存储接口隔离，视图不直接操作 SwiftData 或文件路径。

选择 SwiftData 的原因：

- 当前最低系统版本为 macOS 15，平台能力满足要求。
- 后续资料列表、语言归属和迁移比散落的 UserDefaults 更适合结构化持久化。
- 测试可以使用内存容器，不依赖真实用户数据目录。

### 2. 单主窗口与应用级计时所有者

首版只提供一个主窗口。应用创建一个 `StudyTimeController`，控制器维护：

- 当前展示的语言空间 ID；总览页对应 `nil`。
- 当前激活的语言空间 ID。
- 当前激活周期的单调时钟起点。
- 每个语言空间已经持久化的累计秒数。

视图只能发送以下意图：

- 激活语言空间。
- 离开语言空间。
- 应用进入或离开活跃状态。
- 系统即将休眠或应用即将终止。

控制器不提供设置或调整累计时长的公开接口。

“当前展示空间”和“当前激活空间”不能合并：应用失去焦点时需要暂停计时，但重新激活后仍要知道主窗口停留在哪个语言空间，从而自动恢复。

### 3. 计时状态转换

激活语言空间时：

1. 将目标记录为当前展示空间。
2. 如果应用当前非活跃，只更新展示空间，不启动计时。
3. 如果目标空间已经激活，不创建第二个计时起点。
4. 如果另一个空间正在计时，先将它从起点到当前时刻的增量提交到累计值。
5. 将目标空间设为唯一激活空间，并记录新的计时起点。

暂停时：

1. 计算当前起点到暂停时刻的非负增量。
2. 将增量加入当前语言的累计秒数并持久化。
3. 清空当前激活空间和计时起点，但不清空当前展示空间。

离开语言空间时：

1. 提交当前激活空间的增量。
2. 清空当前激活空间、计时起点和当前展示空间。

应用重新激活时：

1. 如果当前展示空间为空，保持暂停。
2. 如果当前展示空间存在且没有运行中的计时区间，为它创建新的计时起点。
3. 重复激活、暂停、休眠或唤醒事件必须幂等，不能重复提交增量。

应用重新启动后，计时状态默认为暂停。不会根据上次保存的墙上时钟时间补算关闭期间的时长。

### 4. 时间精度与异常恢复

- 运行时增量使用 `SuspendingClock` 计算，避免用户修改系统时间造成负值或跳变，并避免系统休眠期间时钟继续增长。
- 累计值以秒保存，禁止在存储层按 `0.1` 小时取整。
- 界面将秒转换为小时并显示一位小数。
- 正常切换空间、进入非活跃状态、关闭窗口、系统休眠和应用退出时立即提交。
- 系统休眠通知作为额外暂停信号；事件重复或乱序时按照当前状态幂等处理。
- 活跃期间每 30 秒尝试写入检查点。以同一个采样时刻计算增量；只有累计值成功持久化后，才把计时起点推进到该采样时刻。
- 检查点写入失败时，累计值和计时起点都保持原状，并向界面暴露未保存状态；下一次检查点重新提交完整未保存增量。
- 增量保留时钟提供的精度，不在检查点阶段截断为整秒。
- 正常生命周期事件保存成功时不丢失时长。异常退出最多丢失上次成功检查点之后的增量；连续存储失败时无法承诺固定上限，界面必须提示未保存状态。
- 检查点只更新累计值，不创建学习会话历史。

### 5. 资料导入与删除一致性

资料导入使用带状态的两阶段流程：

1. 校验文件类型和读取权限。
2. 生成稳定、无冲突的应用内目标路径，并将原文件复制到 `.staging` 临时目录。
3. 创建状态为 `importing` 的 SwiftData 元数据并提交。
4. 将临时文件原子移动到正式资料目录。
5. 将元数据状态更新为 `ready`。

启动时对 `importing` 元数据和 `.staging`、正式资料目录进行对账：能够完成的导入继续完成，无法完成的导入删除元数据和残留文件。只有 `ready` 资料对用户可见。

资料删除使用应用内 `.trash` 目录：

1. 将元数据标记为 `deleting`。
2. 将正式文件原子移动到 `.trash`。
3. 删除 SwiftData 元数据。
4. 清理 `.trash` 中的文件。

启动时继续处理 `deleting` 元数据并清理无元数据引用的 `.trash` 文件。这样中途失败不会产生用户可见的失效资料，也能恢复正式目录中的孤立文件。

## 后果

正面影响：

- 日语和英语可以独立累计，但不会同时计时。
- 页面切换和应用生命周期共享同一事实来源。
- 不需要保存单次学习记录，也能可靠恢复累计值。
- 文件复制和元数据写入的职责清晰，后续可独立测试。

代价：

- 需要处理 SwiftData 模型迁移和 Application Support 文件生命周期。
- 周期性检查点会增加少量本地写入。
- 自定义头像、动态语言和附件支持都需要未来单独设计。

## 不采用的方案

### 每个语言页面持有自己的计时器

页面重建或导航切换时容易重复计时，无法维护全局互斥约束。

### 只保存启动时间并在下次启动补算

无法区分用户真实学习时间和应用关闭时间，会产生明显虚假累计。

### 保存每次学习会话

当前产品只需要类似 Steam 的累计时长。会话历史会扩大产品范围，并引入用户暂不需要的学习记录语义。

### 使用 UserDefaults 保存所有数据

它适合少量偏好，但不适合未来增长的资料元数据、语言归属和迁移需求。
