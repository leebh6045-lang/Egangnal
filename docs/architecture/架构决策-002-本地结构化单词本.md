# ADR-002：本地结构化单词本

- 状态：已接受
- 日期：2026-08-10

## 背景

单词本需要从固定 Markdown 模板导入词条，并支持默认去重分页、按文档日期查看、首次释义优先和高频词判断。它与复制后只读的学习资料不同：原始 Markdown 只是用户填写和交换数据的载体，应用真正使用的是解析后的结构化记录。

## 决策

### 1. 使用 SwiftData 本地持久化

继续使用应用已有的 SwiftData 容器，底层由系统管理本地 SQLite。用户无需安装、启动或维护数据库服务，也不引入 MySQL、云端或第三方依赖。

### 2. 分离主词条、导入批次和出现记录

- 主词条保存当前展示的单词和首次释义，作为默认分页的数据源。
- 导入批次保存文档日期、导入时间和来源文件名，用于诊断一次成功导入。
- 出现记录连接主词条与文档日期，作为日期模式和高频判断的数据源。

仅在主词条上保存日期集合会使查询和约束变复杂；每次导入都复制完整词条又无法可靠实现默认去重和首次释义优先，因此不采用这两种结构。

### 3. 唯一键保证幂等与语言隔离

主词条唯一键包含语言空间和规范化文本，出现记录唯一键包含语言空间、主词条 ID 和文档日期。同日重复导入不会产生第二条出现记录，不同语言空间的数据不会共享唯一键。

### 4. 解析与写入分层

解析器是无数据库依赖的纯逻辑，只接收 UTF-8 数据并返回已校验文档。仓储负责 SwiftData 查询、合并和事务提交。视图与文件选择器不能直接拼接唯一键或修改模型。

一次导入只在全部解析成功后开始写入，并只执行一次保存。保存失败回滚上下文，从而保证批次、主词条和出现记录不会部分可见。

模型使用 UUID 标量外键，由单一仓储集中执行级联删除。仓储必须先完成所有可失败查询，再修改上下文，并在任意失败路径统一回滚。正式持久容器无法创建时，单词本写操作直接失败，不允许退化为退出即丢失的内存写入。

### 5. 高频状态是派生值

高频词定义为同一规范化词至少出现在两个不同文档日期。模型不保存可失真的 `isHighFrequency` 布尔值，而是根据出现日期数计算。手动新增没有日期，不参与高频计数。

## 后果

正面影响：

- 默认模式和日期模式各自拥有直接、清晰的数据源。
- 同日幂等、跨日高频与首次释义规则可以独立测试。
- 结构化数据量很小，通常数万词条仍只占用几十 MB 以内的本地空间。

代价：

- 一个导入词会产生主词条之外的出现记录，查询需要在仓储层组合结果。
- 唯一键规则属于持久化协议，未来修改规范化算法时需要显式迁移。
- SwiftData 的 SQLite 文件属于实现细节，不承诺用户直接编辑数据库；正式备份与迁移功能需另行设计。

## 不采用的方案

### 将每份 Markdown 作为只读资料保存

无法可靠完成去重、分页、高频判断和条目级编辑。

### 使用 UserDefaults 或 JSON 数组

数据增长后缺少索引、唯一约束和事务，跨日期查询与原子更新的维护成本更高。

### 部署 MySQL

单用户本地应用不需要数据库服务进程、账号、端口和运维成本；SwiftData 已满足当前查询和持久化需求。
