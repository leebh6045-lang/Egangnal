# ADR-003：公共词库与个人单词本分离

- 状态：已接受
- 日期：2026-09-11
- 分发处置：方案 A —— 公开分发，保留 MIT 署名与许可证文本，首版排除 `collins`、`oxford`、`audio`、`detail` 字段（见《ECDICT 离线词库构建契约》第 3 节）

## 背景

“学习资料”需要新增**词库**：内置海量英语词条，按初中、高中、四级、六级分级，支持搜索和词义遮盖，并允许把生词**收录**到个人单词本。日语词库本阶段搁置。

现有 SwiftData 模型服务于个人单词本，语义是“用户自己导入或新增的词”：

- `WordEntry`：个人空间中的主词条与首次释义。
- `WordImportBatch`：一次 Markdown 模板导入。
- `WordOccurrence`：主词条出现在哪个文档日期。

词库词条的规模（数万条）、生命周期（随版本整体替换）和写入权限（只读）都与个人单词本相反。如果把公共词条全部创建为 `WordEntry`，会造成：

- 用户从未收藏的词出现在个人单词本；
- SwiftData 容器无意义膨胀，首次启动产生大量写入；
- 数据升级与个人数据迁移耦合；
- 现有分页、日期浏览、高频词和单词刷抽题语义被污染。

## 决策

### 1. 公共词库与个人数据物理分离

```text
EgangnalLexicon.sqlite
    公共 / 只读 / 随 App 打包 / 可整体替换 / 带 schema_version

SwiftData
    个人 / 可写 / 需要迁移 / 长期保留
```

词库使用独立文件，不注册为 SwiftData 模型，也不与个人词条共享唯一键空间。

### 2. 词库不写入 SwiftData，收藏才产生 `WordEntry`

浏览词库是纯只读行为，不产生任何持久化写入。只有用户显式点击“加入单词本”，才创建或复用一条 `WordEntry`。

### 3. 词库随 App 打包，不使用服务端

词库数据量在数 MB 量级（详见《词库实现设计》第 8 节），因此采用本地只读 SQLite：离线可用、可复现、可单元测试，且不需要网络层、鉴权、缓存和运维。这保持 ADR-001 的“本地优先”与 README 的“无云端服务和第三方运行时依赖”。

只有出现“词库需要高频更新且不想发版”“多设备同步”或“数据量增长到数百 MB 以上”时，才重新评估，且应优先考虑“服务端只提供增量更新包、本地仍是 SQLite”。

### 4. 收藏写入「当日」出现记录，来源用显式枚举表达

> **2026-09-11 修订**：本节原为「收藏不写 `WordOccurrence`」。实际使用后发现，用户在词库遇到的生词如果不计入当天，就不会出现在当天的日期分组里，与“浏览词库也是学习”的实际体验不符。现将决策改为：**收藏计入当日出现记录**，并用**批次来源**把词库收藏与文档导入区分开。下面保留原始分析与修订后的完整规则。

**原始顾虑（仍然成立的部分）**：如果无法区分来源，收藏产生的记录会与文档导入的记录混在一起，导致无法安全地撤销收藏。

**修订后的规则**：

1. 收藏时创建（或复用）当天的**词库收藏批次**（`WordImportBatch.source == .lexiconCollection`），并在其下写入一条当日出现记录。
2. 同一词同一天重复收藏保持幂等（出现记录唯一键已包含语言、词条与日期）。
3. **正常使用下，一个词最多只有一条收藏记录**。收藏按钮只有“已收藏 / 未收藏”两态，已收藏时再次点击是**取消**而不是再记一次，因此界面无法在同一词上累积出多个收藏日期。
   数据模型与仓储允许一个词存在多条（不同日期）收藏记录，但那是为了在异常路径下保持自洽，不是日常行为。
4. **取消收藏删除该词的全部词库收藏记录**（按第 3 条，日常就是那一条）。这里刻意不区分日期：按钮是二元状态，若只删某一天，其余记录会让按钮仍显示“已收藏”，用户会以为点击没生效。
   无论删除范围如何，**绝不触碰文档导入与手动新增的内容**：若该词另有这两种来源，词条与其文档日期原样保留；只有当词条唯一来源就是词库收藏时才整体删除。
5. “日期模式”因此同时收录文档导入与词库收藏；两者的分组都基于真实发生日期。

`WordOccurrence` 的语义随之从“出现在某份 Markdown 文档的某个日期”扩展为“在某个日期出现过”，来源由所属批次区分。

`WordEntry` 与 `WordImportBatch` 都使用显式来源枚举（`markdownImport` / `lexiconCollection` / `manual`），替代原来的 `isManuallyCreated: Bool`。这符合《开发规范》第 4 节“用类型表达有效状态，避免依赖多个布尔值组合”。

### 5. 稳定来源标识与确定性 ID

- SQLite 中每条词条拥有稳定 `source_id`（由来源词形派生），**不依赖自增主键作为跨版本身份**。
- 构建期为每条词条生成**确定性 UUID**（由 `source_id` 与固定命名空间散列派生），使重建数据库后身份不变，也让 `WordQuizCandidate.id: UUID` 这一现有接口无需改动。

### 6. 只读访问与参数绑定

仓储以 `SQLITE_OPEN_READONLY` 打开数据库；所有查询使用参数绑定，禁止拼接用户输入；打开时先校验 `schema_version`，不兼容时返回明确错误而不是继续查询未知结构。使用系统自带 `libsqlite3`，不引入第三方运行时依赖。

## 后果

正面影响：

- 个人单词本的语义、迁移路径和现有测试完全不受词库规模影响。
- 词库可随版本整体替换、可回滚、可在构建期做一致性校验。
- 高频词、日期模式、分页和单词刷抽题规则保持不变。
- 离线可用，没有网络失败路径。

代价：

- 需要一条离线构建链路（开发期 Python 工具 + SQLite 产物），以及一次 SwiftData 轻量迁移（`isManuallyCreated` → `source`）。
- 公共词库与个人词条是两个数据源，单词刷的候选层需要显式合并两者。
- 词库更新依赖发版；在本阶段这是可接受的。

## 不采用的方案

### 把公共词条全部导入 SwiftData

破坏个人单词本语义，容器膨胀，首启大量写入，迁移与升级耦合。

### 服务端数据库或在线词典 API

引入网络层、可用性、延迟、隐私和运维成本，离线不可用，且违背产品定位；搜索性能也不会优于本地索引。

### 在运行时解析 ECDICT 原始 CSV 或 JSON

每次启动都要解析大量文本，启动变慢、无法建索引、格式变化会直接影响 App；转换必须发生在开发期并固化为可校验的产物。

### 用 `WordOccurrence` 表示收藏日期

按决策 4 的理由，会同时污染高频词与日期模式两条既有规则。
