# Egangnal 开发规范

## 1. 迭代原则

- 每次只解决一个清晰问题，避免跨阶段提前实现。
- 大阶段开始前必须有需求、数据结构、风险和验收标准文档。
- 行为变更必须同步更新对应文档和测试。
- 不为了未来假设提前引入抽象；只有明确减少复杂度时才增加层次。
- 每次改动都应保持工程可构建、核心测试可运行。

## 2. 代码组织

- `App` 负责应用生命周期、全局命令和依赖组装。
- `Features` 按用户可感知的功能组织界面与业务协调。
- 领域状态不直接堆叠在根视图中。
- 本地存储通过明确接口访问，视图不直接读写文件系统。
- 应用级计时器只有一个所有者，主窗口只发送页面和生命周期意图。
- 资料正文和结构化元数据分开管理。
- 单词本通过解析器和仓储访问，视图不直接解析 Markdown 或操作 SwiftData。

## 3. 中文注释

代码标识符保持清晰的英文命名，注释使用简洁中文。

应当注释：

- 为什么采用某个状态转换或存储策略。
- 容易被破坏的业务不变量。
- 系统生命周期、并发或文件操作中的异常边界。
- 不能从代码本身直接看出的权衡。

不应注释：

- 对下一行代码做逐字翻译。
- 重复类型、函数或变量名称已经表达的信息。
- 已失效的临时计划和无负责人 TODO。

示例：

```swift
// 切换空间前先提交旧空间的增量，保证任意时刻只有一个语言累计时长。
commitActiveSpace(at: now)
```

## 4. 状态与健壮性

- 用类型表达有效状态，避免依赖多个布尔值组合。
- 累计时长内部使用精确秒数，显示格式不能反向污染存储值。
- 时长只能通过计时控制器的状态转换增加，不能暴露任意 setter。
- 时间差使用 `SuspendingClock` 计算，防止系统时间修改和系统休眠造成错误增量。
- 当前展示空间与当前运行中的计时区间必须分开建模，不能用一个可空 ID 同时表达两种状态。
- 检查点只有在累计值成功持久化后才能推进计时起点；失败时两者必须同时保持原状。
- 文件导入和删除采用带状态的两阶段流程，启动时必须能够对账恢复。
- 单词导入先完整解析和校验，再用一次保存提交全部变化；解析失败不能触碰数据库。
- 主词条与出现日期分开建模，同日重复导入必须幂等，高频状态只能由不同日期数派生。
- 本地写入失败必须保留上一个有效状态。
- UI 更新和持久化操作必须遵守 Swift 6 并发隔离。

## 5. 测试要求

### 单元测试

优先覆盖：

- 进入、切换、离开语言空间的计时状态转换。
- 重复激活同一空间不会重复计时。
- 非活跃、休眠和退出时正确提交增量。
- 应用失去焦点后暂停，重新激活时按当前展示空间恢复。
- 重复或乱序的休眠、唤醒、暂停事件保持幂等，不重复提交时长。
- 小数小时格式化不改变内部秒数。
- 文件复制失败、重名以及导入或删除中断后的恢复行为。
- 单词模板的日期、空行、空格和全角分隔符字节协议。
- 单词解析错误、跨导入去重、首次释义优先、同日幂等和语言隔离。
- 高频词的不同日期阈值，以及分页 0、1、20、21、40、41 条边界。

### UI 测试

- 使用页面独有标识证明导航确实发生。
- 避免使用多个页面共有的文案作为唯一断言。
- 至少覆盖总览到两个语言空间的核心路径。

## 6. 每步质量门槛

完成一个小阶段前应当：

1. 审查 `git diff`，确认没有无关改动和用户状态文件。
2. 执行 Debug 构建。
3. 执行相关单元测试。
4. 行为涉及导航或窗口时执行核心 UI 测试。
5. 检查最小窗口、深色模式和关键辅助功能标识。
6. 更新产品、架构或路线图文档中的状态与决策。
