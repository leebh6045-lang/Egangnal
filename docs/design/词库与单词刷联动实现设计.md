# 词库与单词刷联动实现设计（阶段 5.5）

- 状态：已完成（2026-09-13 实现并验收；选项已由用户确认）
- 日期：2026-09-13
- 关联文档：[词库实现设计](词库实现设计.md) 第 6 节；[ADR-003](../architecture/架构决策-003-公共词库与个人单词本分离.md) 决策 4、5；[开发路线图](../开发路线图.md) 阶段 5.5；[开发规范](../开发规范.md)

## 1. 目标与范围

让**词库收藏的生词**真正能被单词刷抽到，并保证抽到的选项在同一题内可辨认。

本阶段（5.5）**只做必做项**：

1. 用测试锁定「收藏词条已在默认抽题池中」这一既成事实，并覆盖取消收藏后的退出。
2. 修复组卷时的**选项显示冲突**：同一题内两个选项的显示文本可能完全相同，用户无法分辨。

**明确后置到 5.5.1**：在等级结果或搜索结果上直接发起单词刷（原设计第 6.3 节「等级速测」）。后置原因见第 3.4 节——它需要改动 `WordQuizScope` 的承载能力与一条跨工作区请求通道，不属于"小步可独立验证"的范围。

**本阶段不改动**：`WordQuizEngine` 的领域契约（题目结构、评分、错题重做、难度分支）、单词本读写、词库只读查询层、界面导航。

## 2. 现状核实（动手前的实测结论）

交接说明第 6.2 节要求"动手前先核实第 1 条是否已满足"。核实结果：

| 结论 | 依据 |
| --- | --- |
| 收藏词条**已经**进入默认抽题池 | `WordQuizCandidateSource.isImported` 的判定是 `!entry.occurrenceDates.isEmpty`；而 5.3.2 起 `SwiftDataWordBookRepository.collectFromLexicon` 会创建当天的「词库收藏批次」并写入一条当日出现记录 |
| 未收藏的词条**不会**进入 | 词库词条不写入 SwiftData，`repository.entries(in:)` 根本读不到它们 |
| 取消收藏后**会自动退出** | `uncollectFromLexicon` 删除词库收藏的出现记录；唯一来源是收藏时连词条一并删除 |
| 收藏写入的释义已足够短 | `LexiconCatalogStore.collect` 写入 `LexiconGlossFormatter.browsingDisplay(...).text`，上限 12 字符，适配 `AppTheme.wordQuizChoiceWidth × wordQuizChoiceHeight`（136 × 78） |

因此第 1 条**不需要重复实现**，只需补测试锁定。这一点与《词库实现设计》第 6.1 节「当前进不了单词刷，必须显式修改」的原始判断相反——该判断写在 5.3.2 修订收藏规则之前，现已过时，本次一并更正文档。

### 2.1 一处需要澄清的细节：写入的是 `browsingDisplay` 而不是 `shortGloss`

两者都限长 12 字符，差别在**是否保留词性前缀**：

| 派生 | 输入 | 输出 |
| --- | --- | --- |
| `LexiconGlossFormatter.shortGloss` | `vt. 放弃, 抛弃, 遗弃` | `放弃` |
| `LexiconGlossFormatter.browsingDisplay` | 同上 | `vt. 放弃, 抛弃…` |

收藏链路用的是后者，因此单词刷选项上会显示带 `vt.` 前缀的形态。**本阶段不改**：理由是它与词库列表、单词本中显示的文本一致，用户在三个页面看到同一条释义；改成 `shortGloss` 反而会让单词本里的释义文本发生变化。此项记录为可评估项（第 6 节）。

### 2.2 真实数据的冲突规模（实测）

> **2026-09-13 更正**：本节初稿曾用 `shortGloss`（去词性前缀）估算，得出"891 组、2,073 条词"。
> 那个数字对应的**不是**单词本里实际存储的文本，已作废。下表是按收藏链路真正使用的
> `browsingDisplay`（保留 `vt.` 前缀、按完整义项累加）对全部 7,116 条词条重新实测的结果。

| 指标 | 实测值 |
| --- | --- |
| 显示文本互不相同的词条 | 7,020 条 |
| 显示文本相同、但**完整释义不同**的分组 | **93 组，涉及 189 条词** |
| 显示文本触到 12 字上限（长度 = 13）的词条 | **684 条** |
| 单行释义被上限切掉的词条（排除多行造成的省略号） | 111 条 |
| `isTruncated` 标志为真的词条（含义是"还有更多可看"，多行也算） | 6,271 条 |
| 显示文本最长长度 | 13 字符（12 字 + 省略号） |
| 典型例子（截断造成） | `absolutely` / `altogether` / `completely` / `perfectly` → 都是 `adv. 完全地…` |
| 典型例子（英美拼写变体） | `aeroplane` / `airplane` → 都是 `n. 飞机…`（释义逐字相同） |
| 典型例子（同义近义） | `analyse` / `analyze`、`aluminium` / `aluminum`、`alike` / `like` |

⚠️ 上表三个"截断"口径相差近十倍，引用时必须写明是哪一个：684 是"显示文本触到上限"，
111 是"单行释义真的被切掉"，6,271 只是"还有更多内容可看"。**只有前两个能说明文字被切。**


结论有两条：

1. **冲突是真实存在的**（93 组），而且在候选池足够大时必然会发生——单词刷一次抽 20 题，
   每题 4 个选项，命中同组两个词的概率不低。
2. 冲突**主要来自截断**（684 条词条的显示文本触到 12 字上限），也有相当一部分来自词典本身
   （英美拼写变体、近义词）。因此"放宽长度上限"只能缓解其中一类，不能解决另一类；而"换干扰项"对两类都有效。

**同时要更正一个曾被误判的例子**：`detect`（`vt. 发现, 察觉, 探测`）与 `detection`（`n. 发现, 察觉, 探测`）
的显示文本**并不相同**，因为 `browsingDisplay` 保留了词性前缀。它们不会造成显示冲突，只是词义相近而已。

### 2.3 冲突检测还要覆盖"界面文本与判定文本同源"

引擎按 `displayText` 判重，界面直接渲染释义字段。今天两者恰好相等（写进单词本的释义已经是派生结果），
但这是**依赖关系而不是巧合**，必须由测试锁定：一旦将来把完整释义直接传进引擎，
而引擎忘了接上派生规则，就会出现"引擎认为没有冲突、用户看到两条一样的选项"。

## 3. 设计

### 3.1 必做项一：候选来源锁定

不改代码，只补测试。测试从**真实仓储入口**出发，而不是伪造快照，避免"测试通过但产品不成立"：

```text
0. 建一个内存 ModelContainer
1. SwiftDataWordBookRepository.collectFromLexicon(term:meaning:collectedAt:in:)
2. WordQuizCandidateSource.allImportedCandidates(in:)
   → 断言收藏词在候选里，且释义与写入时一致
3. uncollectFromLexicon(term:in:)
   → 断言候选为空
```

同时补一条"未收藏的词库词条不在候选里"的反向断言：用真实的 `SQLiteLexiconRepository` 取一页词条，断言它们的 id 都不在候选集合中。这条断言锁的是 ADR-003 决策 2（浏览词库不写 SwiftData）。

### 3.2 必做项二：选项显示冲突

**为什么必须现在处理**：用户看到两个显示相同的选项时，选哪个都由 `WordQuizEngine.evaluate` 按 `optionID` 判定，等于让用户凭运气选；而这在 93 组、189 条词的规模下不是理论风险。

**为什么放在组卷而不是收集时**：

- 收集时去重会**改写写进个人单词本的释义文本**，污染用户数据（已否决）。
- 组卷时处理只影响这一次抽题结果，可回滚、可单测、不改任何持久化内容。
- 与《词库实现设计》6.2 的原始要求一致：「冲突时放宽长度上限或改选其他干扰项」。

**"显示文本"的定义**：在引擎内新增纯函数 `displayText(of:)` 作为**唯一判定依据**，与界面渲染的
`meaning` 字段取值相同。它当前折叠空白后原样返回——因为写进单词本的释义已经是
`LexiconGlossFormatter.browsingDisplay` 的产物；将来若把**完整释义**直接传进引擎，
只需在这里接上派生规则，冲突检测自动生效，**但必须同时保证界面渲染的是同一个函数的返回值**。
这条等式由 `browsingDisplayMatchesTheQuizDisplayTextForEveryEntry` 对全部 7,116 条词条锁定。

**算法**（在 `makeMeaningQuestion` 的干扰项挑选过程中，两道闸门，缺一不可）：

```text
usedMeanings      = { 目标词的完整释义 }      // 挡"释义重复的重复词条"（原有逻辑）
usedDisplayTexts  = { 目标词的显示文本 }      // 挡"看起来一样的不同释义"（新增）

对每条候选干扰项 d：
    若 完整释义 ∈ usedMeanings       → 跳过
    若 显示文本 ∈ usedDisplayTexts   → 跳过
    否则 → 登记两者，选为干扰项
若候选池遍历完仍凑不齐 3 个干扰项 → 抛 insufficientDistinctMeanings(4, 实际可用的显示文本数)
```

**为什么不做"放宽长度上限"**：684 条词条被截断确实制造了冲突，但英美拼写变体与近义词那一类
（如 `aeroplane` / `airplane`，释义逐字相同）无论把上限放到多少都躲不开；而放宽上限还会让选项文本变长，
挤压 136 × 78 的按钮。因此本阶段只做"换干扰项 / 丢弃干扰项"，它对两类冲突同时有效。

**为什么错误信息里报的是显示文本数**：若 `available` 按完整释义计数就会虚高——
被显示文本挡掉的候选其释义并没有真的可用。因此 `acceptDistractor` 在两道闸门都通过后才登记释义。

### 3.3 边界与不变量

1. 冲突检测**只作用于干扰项**，不影响目标词条；目标词条即使与其它词显示相同也照常出题。
2. 检测在**同一题内**进行，跨题不做任何约束（两道题可以出现相同选项文本）。
3. 干扰项不足时**明确失败**，不静默降级成"两个选项的单选题"——选项数量是四选一的产品契约。
4. 冲突判定使用与界面完全相同的文本来源；若将来界面改变渲染方式（截断、加后缀），必须同步改 `displayText(of:)`。
5. 本阶段只处理**显示文本完全相同**；语义近义（如「完全地」与「彻底地」）仍会出现，见第 6 节。

### 3.4 为什么等级速测后置

原设计 6.3 节的"新增等级范围分支"在这份代码里有两个未解决的接口约束：

1. `WordQuizScope` 是 `Hashable, Sendable`，**装不下** `[LexiconEntry]`（`LexiconEntry` 只有 `Equatable`）；而"范围 = 当前筛选"在搜索场景下不是等级枚举能表达的。
2. 该范围的干扰项池应当是**整个词库 7,116 条**，而 `WordQuizStore.load()` 目前只从个人单词本读候选，需要一条独立的词库候选加载路径。
3. 从词库页发起还需要一条**跨工作区请求通道**（`LexiconView` → `ContentView` 路由 → `WordQuizView` 的初始状态），目前不存在。

这三项都属于结构性改动，适合独立成一个阶段（5.5.1）单独设计、单独验收。本阶段不做，避免一次改动同时触碰候选层、组卷层与导航层。

## 5. 风险与验收

| # | 风险 | 处理 |
| --- | --- | --- |
| 1 | 冲突检测把干扰项池筛得太小，导致原本能出的题变成报错 | 显示文本冲突只有 93 组、每组 2–4 个成员，占全库不到 3%；而默认范围的干扰项池是全部可抽题词条（文档导入 + 词典收藏），超过 400 条时不可能凑不齐 3 个干扰项。测试用例专门锁定"被拒的候选会被后续候选顶替，选项数仍是 4" |
| 2 | 显示文本规则分散在引擎与界面两处，将来漂移 | 由全库测试（7,116 条）锁定"界面渲染的文本经过 `displayText(of:)` 后不变"；一旦漂移立刻失败 |
| 3 | 误把"完整释义去重"删掉，让重复词条同时成为选项 | 两道闸门都保留，并各有用例锁定（`strictChoiceModeRejectsFewerThanFourDistinctMeanings` 与新增用例） |
| 4 | 端到端候选用例依赖真实 SQLite 与 SwiftData，可能因环境失败 | 词库缺失时按 `LexiconTestSupport` 的既有约定**明确失败**，不静默跳过 |
| 5 | 冲突基线数字随数据或规则变化而失效 | 基线用例显式断言 684 / 93 / 189 三个数字，并在失败信息里给出对照，便于判断是"规则变粗糙"还是"数据换了版本" |

验收标准：

- 收藏词条可被单词刷抽到；未收藏的词库词条不会出现在默认范围中；取消收藏后退出候选。
- 同一题内不存在两个显示文本相同的选项；凑不齐干扰项时给出明确错误而不是少给选项。
- `WordQuizEngine` 的题目结构、评分、错题重做与难度分支行为不变。
- 长释义经派生后不破坏四选一选项布局（沿用 136 × 78 的既有常量，不新增尺寸）。

## 6. 记录为后续评估项（本阶段不做）
