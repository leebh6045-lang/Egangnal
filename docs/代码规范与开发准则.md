# Egangnal 代码规范与开发准则

> **本文的定位**：项目在长期迭代中必须遵守的工程约定总纲。它回答三个问题——**什么样的改动可以进入代码库**、**代码应该写成什么样**、**做完一步之后要交出什么**。
>
> **与《开发规范》的关系**：`docs/开发规范.md` 是本文第 4、7 节的具体展开，两者冲突时以本文为准，并应在同一次改动中把《开发规范》对齐；专项规则（如《ECDICT 离线词库构建契约》）在其适用范围内优先级最高。
>
> **适用范围**：`Egangnal/`、`EgangnalTests/`、`EgangnalUITests/`、`tools/` 下的全部代码，以及 `docs/` 下的文档。
>
> **基线**：macOS 15.0+、Swift 6、Xcode 16.4+。

## 1. 七条最高准则

当具体规则没有覆盖眼前的情况时，按这七条自行判断。

| # | 准则 | 含义 | 反面例子（本仓库真实踩过） |
| --- | --- | --- | --- |
| 1 | **小步推进** | 一次改动只解决一个清晰问题，可构建、可测试、可单独回退 | 把"浮层定位"和"收藏规则"混在一次改动里 |
| 2 | **文档先行** | 大阶段开始前先有需求、数据、风险与验收文档 | 直接照着感觉写 5.6 资料导入 |
| 3 | **文档与代码同步** | 行为变了，测试和对应文档必须在同一次改动里更新 | 改了收藏规则却留着"收藏不写出现记录"的旧结论 |
| 4 | **低耦合** | 界面不知道数据库怎么查，业务规则能脱离窗口单测 | 视图里直接 `ModelContext.fetch` |
| 5 | **类型优先** | 用枚举和明确模型表达状态，不用多个布尔值互相组合 | 用两个 `Bool` 表示"已收藏 / 是导入的来源" |
| 6 | **根因优先** | 修根因，不掩盖；不静默降级、不伪造结果 | 为了"看起来通过"而放宽断言 |
| 7 | **不为假设提前抽象** | 只有确实降低复杂度时才增加一层；不引入用不上的依赖 | 还没第二个实现就先抽三层协议 |

第 7 条不是第 4 条的反面：**协议用于隔离已经存在的变化**（真实实现 / 预览 / 测试替身），而不是用来预演想象中的未来。

## 2. 分层与依赖规则

### 2.1 五层职责

```text
Features（页面与交互）
    ↓ 只表达布局和用户意图
Stores（可观察状态与流程协调）
    ↓ 只调用业务接口
Domain（领域模型与纯业务规则）      Data（仓储协议与系统边界实现）
    ↓                                  ↓
        SwiftData / UserDefaults / 文件系统 / SQLite / AVFoundation / Sparkle
```

| 层 | 允许做 | 明确禁止 |
| --- | --- | --- |
| `App/` | 生命周期、路由、窗口、菜单命令、依赖组装 | 具体业务规则 |
| `Domain/` | 模型、枚举、纯计算、解析、格式化 | 依赖 SwiftUI 视图、直接读写数据库 |
| `Data/` | 仓储协议与实现、文件系统、外部系统封装 | 出现 SwiftUI 类型；把失败静默吞掉 |
| `Stores/` | `@MainActor @Observable` 页面状态、流程编排、加载/错误态 | 直接画界面；绕过仓储操作持久化 |
| `Features/` | 布局、动画、交互意图、无障碍标识 | 直接操作 SwiftData、直接解析 Markdown、内联 `URLSession` |
| `Design/` | 主题、配色、间距、圆角、共享修饰器 | 只被单个页面使用的私有样式（应留在该页面） |

### 2.2 依赖方向

- 依赖只能从上往下：`Features → Stores → Domain/Data`。**反向引用一律不允许**。
- `Domain` 不依赖 `Stores` 和 `Features`；`Data` 不依赖 `Stores` 和 `Features`。
- 仓储**先声明协议再提供实现**；页面和 Store 依赖协议，不依赖具体类型。
- 需要被替换或需要被单测的外部能力（时间、文件、音频、更新、随机源）**必须通过协议包住**。
- 所有全局对象只在 `App/AppDependencies.swift`（Composition Root）创建一次，不散落 `static let shared` 单例。

### 2.3 命名与目录

- 目录名与层名一致（`Domain`、`Data`、`Stores`、`Features`、`Design`）。
- 一个类型一个文件，文件名与类型名一致。小型私有辅助类型可以同文件，但必须是 `private` 且明显从属于主类型（如 `LexiconGlossDisplay` 之于 `LexiconGlossFormatter`）。
- 功能页放进 `Features/<功能名>/`，一个功能一个目录，不要平铺。
- 工程使用 Xcode 同步根组：**新文件放进目录即自动入 target，不要手工编辑 `project.pbxproj`**。

## 3. 命名与代码风格

### 3.1 命名

- **标识符一律英文**，不使用拼音；注释一律简洁中文。
- 类型用大驼峰，方法与属性用小驼峰；布尔值以 `is` / `has` / `should` / `can` 开头。
- 命名表达**领域含义**而非实现细节：`collectionInfo` 优于 `dict1`；`reshuffle()` 优于 `reset2()`。
- 视图与样式常量复用 `AppTheme`；确需本页专用常量时用 `private static let`。

### 3.2 注释

应当注释：

- **为什么**采用某个状态转换或存储策略，而不是逐行翻译"做了什么"。
- 容易被破坏的**业务不变量**（例如"任意时刻只有一种语言在计时"）。
- 生命周期、并发、文件操作中的**异常边界**。
- 无法从代码本身看出的**权衡与实测数据**。

不要注释：

- 对下一行代码的逐字翻译。
- 重复类型名、函数名已经表达的信息。
- 无负责人、无期限的 TODO。

反例与正例（均取自现有代码）：

```swift
// ❌ 无信息量
// 关闭数据库
sqlite3_close(database)

// ✅ 解释为什么可以 unsafe、为什么这样才安全
/// 标记 `nonisolated(unsafe)` 是为了让 deinit 能关闭连接：句柄在 init 后不再变化，
/// 所有查询都在主 actor 上执行，deinit 运行时已不存在其他引用。
private nonisolated(unsafe) let database: OpaquePointer
```

```swift
// ✅ 把实测数据写进注释，避免后人凭直觉推翻结论
// 子串匹配用不上 B-tree 索引，但释义总字节仅约 208 KB，
// 实测全表扫描 1–2 ms，当前规模不需要 FTS5。
```

### 3.3 注释即契约的场合

以下位置必须写明**约束**，而不只是描述：

- 派生规则的类型：注明规则版本，例如 `static let version = "gloss-v1"`，并写明"规则变化时必须提升版本号并同步更新测试样例"。
- 与外部产物对齐的常量：注明来源文档章节，例如"必须与《ECDICT 离线词库构建契约》第 6 节一致"。
- 有魔法数字的地方：写明数字的来历（实测值、布局测量、协议规定）。

### 3.4 格式

项目**未配置 SwiftLint / SwiftFormat**，格式以现有代码为准：

- 4 空格缩进，不用 Tab。
- 每个源文件顶部保留 `// 文件名` + `// Target 名` 的短头注释。
- `import` 按字母序排列，全部置于文件顶部。
- 单行尽量控制在 100 字符内（含中文注释按显示宽度计）；函数签名过长时按参数换行。
  现有代码中确有少量超长行（最长为 `WordBookView.swift` 的 189 字符），属于历史遗留，
  **新代码不再增加**；改动旧代码时顺手收敛，不做无关的大范围重排。
- 每个类型、每个非平凡方法都写 `///` 文档注释；`private` 辅助函数至少一句话说明用途。

## 4. 状态、并发与健壮性

本节是《开发规范》第 4 节的具体化，凡涉及持久化、时间或文件系统时都必须遵守。

### 4.1 并发模型

- 项目**未开启 `defaultIsolation: MainActor`**，因此隔离域必须逐个显式标注。
- 全部 `Store` 与页面状态标注 `@MainActor @Observable`。
- 仓储协议与其实现标注 `@MainActor`。
- 纯计算类型（无共享可变状态）声明为 `enum` 命名空间并保持 `Sendable`，不要为了"线程安全"强行加锁。
- 跨任务传递的类型尽量满足 `Sendable`；确实不能时，用最小范围的 `nonisolated(unsafe)` 并在注释里写明**为什么安全**。
- 需要后台执行的重活（构建工具、外部进程）不要放进 App 进程的主 actor。

### 4.2 状态表达

- 用**枚举**表达互斥状态，不用多个布尔值组合。
- 累计时长内部只存精确值，显示格式化不得反向污染存储值。
- 时长只能通过控制器的状态转换增加，不暴露任意 setter。
- 时间差用单调时钟（`StudyTimeController` 使用 `SuspendingClock`）计算：它不随用户修改系统时间跳变，且系统休眠期间不计时——这正是计时语义需要的。
- 检查点只有在累计值**成功持久化后**才能推进起点；失败时两者必须同时保持原状。

### 4.3 持久化与文件操作

- 写入失败必须**保留上一个有效状态**，绝不留下"改了一半"的数据。
- 批量导入先**完整解析和校验**，再用一次保存提交全部变化；解析失败不得触碰数据库。
- 文件导入/删除采用**带状态的两阶段流程**（`.staging` → 原子移动 → 标记完成；删除走 `.trash`），启动时能对账恢复。详见《架构决策-001》第 5 节。
- 版本化产物（SQLite 词库、模板格式）必须**校验版本**，不兼容时明确报错，不尝试兼容猜测。
- 公开的分级规则、schema 与质量门槛以《ECDICT 离线词库构建契约》为准，代码常量必须与之一致。

### 4.4 输入校验与失败处理

- 用户输入与外部文件一律**显式校验并明确拒绝**，不做宽松兜底。不支持的类型、缺失的字段、越界的页码都要有确定的错误结果。
- 错误类型用 `Error` + `LocalizedError` 建模，`errorDescription` 面向用户，内部细节（SQL 报文、路径）不要直接抛给界面。
- **禁止**为了"不报错"而静默降级：例如词库打不开时假装返回空列表。应以 `UnavailableLexiconRepository(failure:)` 这类显式失败实现表达，并把原因显示给用户。
- 已知会失败的路径要留可诊断信息（`OSLog` 或错误对象），便于事后定位。

### 4.5 可访问性

- 只靠鼠标悬停/指针位置才能完成的操作**必须**同时提供非指针入口（`.accessibilityAction` 等）。
- 交互组件给出稳定的 `accessibilityIdentifier`，供 UI 测试断言。
- 只依赖颜色传达的信息（如"已收藏"）必须有非颜色的补充语义。

## 5. 测试规范

### 5.1 分层策略

- **单元测试（Swift Testing）**：覆盖纯业务规则、解析、格式化、状态转换、仓储读写。
- **UI 测试（XCTest / XCUITest）**：只覆盖真实窗口下才能验证的东西——导航、布局、无障碍标识、键鼠交互。

判定标准：**能用单元测试证明的，不要写 UI 测试**；但**只靠眼睛才能确认的（布局、焦点、渲染），必须写成 UI 测试**。

### 5.2 命名与结构

- 测试方法描述**行为**而非实现：`truncatedBrowsingDisplayAlwaysEndsWithEllipsis()`，而不是 `testFormatter3()`。
- 一个测试一个主张；参数化用 `@Test(arguments:)`，不要在一个方法里串行断言五件事。
- 测试用到的共享夹具放进 `*TestSupport.swift`，不要复制粘贴。
- 临时数据库、临时目录必须在测试结束前清理。

### 5.3 测试替身

- 替身只用于**隔离慢/不稳定依赖**，不得伪造成功。
- 需要真实验证的环节（词库产物、Markdown 解析、规范化规则）**直接读真实产物与共享样例**（如 `fixtures/normalization-cases.json`），不复制副本。
- 每次仓储协议变化，同一次改动内补齐所有替身的实现。

### 5.4 UI 测试的硬性经验

以下三条都是本仓库真实踩过的坑，属于强制约定：

1. **断言用 `accessibilityIdentifier`，不用可见文案**。文案可能被多个页面共有，也可能随主题/语言变化。
2. **不要用 `typeText` 输入文字**：本机环境中它会插入多余空格（`aban` → `a ban`）。改用 `NSPasteboard` 写入 + `Command-V` 粘贴。
3. **不要在 `LazyVGrid` 里数元素个数**：只实例化可见单元格，数量断言与顺序假设都会假失败。与洗牌相关的断言必须写成**与顺序无关**的形式。

### 5.5 回归纪律

- 用户报告的缺陷，先写成一条**可复现的测试**，再修代码。修完测试必须转绿。
- 只在手工验证中发现的缺陷，事后补一条自动化测试；**不要**只靠"我再看一遍"。
- 发现失败时先分清：是本次改动引入的，还是基线就存在。用 `git worktree` 在基线提交上跑一次对照，再决定处理方式——不要默默改断言。

## 6. 文档规范

### 6.1 文档类型与放哪

| 类型 | 位置 | 回答的问题 |
| --- | --- | --- |
| 产品与需求 | `docs/产品需求.md`、`docs/Egangnal产品故事.md` | 用户要什么、不做什么 |
| 架构决策（ADR） | `docs/architecture/架构决策-00X-*.md` | **为什么**这样定，有哪些取舍 |
| 实现设计 | `docs/design/*实现设计.md` | **怎么做**，边界与验收标准 |
| 界面规格 | `docs/design/*界面设计.md` | 视觉、布局、交互、无障碍标识 |
| 规范性契约 | `docs/design/*契约.md` | 产物格式、schema、质量门槛（冲突时以它为准） |
| 流程教程 | `docs/*保姆级教程.md` | 可复现的操作步骤 |
| 路线图 | `docs/开发路线图.md` | 阶段划分、状态、验收标准 |
| 索引导航 | `词库开发索引.md` | 从哪份文档开始看 |

### 6.2 编写规则

- **大阶段开始前必须已有文档**；文档评审通过后才动业务代码。
- 小修小补（不影响行为、不改数据结构的缺陷修复与体验微调）不需要新文档，但仍必须在同一次改动中同步受影响的既有文档。
- 每份文档开头写清**定位、适用范围、与其他文档的关系**。
- 结论要能验收：写"验收标准"而不是"尽量做好"。
- **修订要留痕**：不删除旧结论，用"**修订**（日期）"标注新结论并说明原因。《架构决策-003》决策 4 是范例。
- 数字必须可追溯：写清来源、测量条件或提交哈希，不写"大概""估计"。
- 文档与代码冲突时，**以当前工作区代码为准**，并立刻修正文档。
- 收尾时把新文档登记到对应索引（`词库开发索引.md` 或 `README.md`），否则等同于不存在。

### 6.3 何时更新哪份文档

| 改动 | 必须同步 |
| --- | --- |
| 新增根页面 / 工作区功能 | `WorkspaceFeature.swift`、路线图、对应界面设计 |
| 改动持久化模型或迁移 | 对应 ADR、实现设计、模型注释 |
| 改动外部产物格式 | 对应契约文档 + 版本号 + 构建工具 |
| 改动用户可见行为 | 对应实现设计 + 测试 + `词库开发索引.md`（若属词库范围） |
| 完成一个子阶段 | 路线图状态 + 索引表格 + 验收记录 |

## 7. 每步的完成定义（DoD）

一个小阶段只有全部满足才算完成：

1. **范围**：只做了这一件事，`git diff` 中没有无关改动、没有用户状态文件、没有调试残留。
2. **构建**：Debug 构建通过，无新增警告。
3. **测试**：先跑相关单元测试，再按需跑全套；UI 相关改动必须跑受影响的 UI 测试。
4. **界面**：最小窗口尺寸、深浅两套主题、键盘操作、关键无障碍标识均已检查。
5. **文档**：产品 / 架构 / 路线图 / 索引中受影响的状态与决策已更新。
6. **记录**：在路线图与（如属词库）索引里写下验收结果，包含实际数字。
7. **提交**：单独提交，信息符合第 8 节格式。

## 8. 提交规范

当前仓库只有一次基线提交，历史信息不作为格式依据，因此从本文起固定如下格式：

```text
<type>: <中文短描述>

<可选：为什么这么改，以及验证方式>
```

- `type` 取值：`feat`（新能力）、`fix`（缺陷修复）、`docs`（文档）、`refactor`（无行为变化的重构）、`test`（测试）、`chore`（工程与杂项）。
- 描述用中文，一句话说清**做了什么**，不超过约 40 字。
- 需要解释取舍或验证方式时写正文；验证方式要具体（跑了哪些测试、结果如何）。
- **一个子阶段一次提交**，不要把多个子阶段压成一个提交。
- 提交前确认 `.gitignore` 覆盖了构建产物、`.lexicon-source/`、签名材料等不应入库的内容。
- **提交时机由用户决定**：代理完成改动后报告状态，不擅自 `commit`、`push` 或改写历史。

## 9. 依赖与工具边界

- **第三方运行时依赖必须先用 ADR 论证**。目前唯一允许的是 Sparkle（更新）。
- 优先使用系统框架：SQLite 用系统 `libsqlite3`、音频用 `AVFoundation`、日志用 `OSLog`，不为小事引入包。
- 构建与数据处理脚本放在 `tools/`，使用**标准库**（Python 3 仅用 stdlib），保证离线可复现。
- 工具必须**确定性**：固定输入产生逐字节一致的输出；需要随机时使用显式种子（现有做法是用命名空间 + 来源标识派生稳定 UUID，而不是取系统随机值）。
- 生成的产物（数据库、报告、清单）要带**版本与来源校验**（如 `sha256_file` 校验、`source_manifest.json`、`build-report.json`），并在契约文档中登记。
- App 只打包运行时真正需要的产物（例如词库只含筛选后的 7,116 条），原始大数据源不入库。

## 10. 新会话接手检查单

在新的会话或由他人接手时，按顺序做：

1. 读 `README.md` → 判断本文档是否适用。
2. 读 `docs/项目技术与代码导览.md`，建立分层与调用链地图。
3. 读 `docs/开发路线图.md` 找到当前阶段与状态。
4. 若涉及词库，读 `词库开发索引.md` 第 1、3、6 节。
5. 动手前确认：这一步属于哪个子阶段、依据哪份文档、验收标准是什么。
6. 收尾时回到第 7 节逐条核对。
